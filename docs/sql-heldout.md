# 冻结提示后的 SQL held-out 验证

本轮按用户要求分别验证分类与解释事实，不再根据新案例调整提示。固定 [协议](../evaluations/sql-heldout-v1/protocol.json)、[事实评分口径](../evaluations/sql-heldout-v1/rubric.md) 和 [系统提示](../evaluations/sql-heldout-v1/system-prompt.txt)；提示版本为 `2`，SHA-256 为 `c2cc4b98f5ca1b1e639889f98a057444bc47e8ff8823f541234d4327dd736c6a`。数据、独立 oracle、取证模板和运行脚本在模型请求前写入 `dataset-lock.json`；哈希不符时不能继续冒充本轮冻结条件。

六个新合成案例没有参与 v2 提示调优。这里的 held-out 指相对于提示调整隔离，**不是代表真实项目分布的外部 benchmark**。本轮不接入日常 `/review` 自动取证，不启用自动排除告警；结果只作人工复核辅助。

## 案例与独立依据

源码在 [sql-heldout fixture](../tests/fixtures/sql-heldout)，独立判断在 [oracle.json](../tests/fixtures/sql-heldout/oracle.json)。每例预先定义一个输入 source 调用和一个真实 JDBC `Statement.executeQuery` sink；存在多条相关控制或传播路径。以下是固定源码下的真值依据，不预先宣称 Tai-e 一定报警或模型一定判断正确。

| 案例 | 真值 | 独立依据 |
| --- | --- | --- |
| G：分支与跨方法汇流 | 真缺陷 | 负数 mode 直接传播输入，正偶数 mode 经 `route` 传播输入；其他常量分支不能排除这两条可行路径。 |
| H：数值区间与嵌套条件 | 固定前提下安全 | 污染赋值仅发生在 `mode < -1` 或 `mode > 2`；唯一 sink 要求 `0 <= mode <= 2`，且 mode 未变化。 |
| I：循环与对象别名 | 真缺陷 | 非负 mode 下 cursor 指向 first，第一轮把输入写进其字段；mode=1 第二轮还有一次写入，sink 读取 first.query。 |
| J：数组索引与赋值顺序 | 固定前提下安全 | 两条分支都只向索引 0 写输入，索引 1 写常量；新数组不逃逸，sink 固定读取索引 1。 |
| K：switch 穿透与后续覆盖 | 真缺陷 | mode=0 路径最终被常量覆盖，但 mode=1、2 的污染仍到达 sink；否定前者不足以排除整条告警。 |
| L：异常路径与 finally | 固定前提下安全 | try 和两个 catch 均可能写污染，随后 finally 无条件覆盖同一字段；所有到达 sink 的路径都已完成覆盖。 |

共同前提是输入不可信、目标是固定账户查询，而非授权 SQL 控制台；分析使用保存的源码/规则，局部对象没有外部并发修改或插桩。真缺陷由真实 H2 执行寻找改变 SQL 与结果行的反例；安全结论来自覆盖相关输入和路径的代码论证，有限测试仅作佐证。测试通过也可能表示成功复现漏洞。

## 运行

使用既有 JDK 17/Maven Docker 镜像和缓存，环境要求见 [Maven 检查](maven-check.md)。默认离线：

```powershell
npm run test:sql:heldout
```

需要准备依赖时显式使用 `npm run test:sql:heldout -- --prepare-dependencies`。将分析输出的结果路径交给模型验证：

```powershell
npm run test:sql:heldout:review -- "分析运行目录/result.json"
```

每条实际项目污点告警请求一次固定 DeepSeek 模型，无工具、无编码历史、无重试。输入提供同一历史快照的完整案例类、Main 和污点策略，以及原告警/路径；不发送测试源码、SQL 独立观测、oracle、期望答案或评分锚点。源码、提示、配置与响应原文均记录指纹。未报告案例、构建/分析/请求失败全部保留，不伪造告警或挑选模型答得好的案例。

收到响应后，对 `ruleClaim`、`rationale`、`assumptions` 和 `missingEvidence` 中具体事实逐项核对，保存引述、原子主张、证据位置与判定到 `fact-review.json`。这是 agent-assisted、provisional 的核对，须能由人复验；不是模型自己给自己打分，也不表示已有人工批准。评分命令只校验记录来源和计算指标，不自动证明主张为真：

```powershell
npm run test:sql:heldout:score -- "复核运行目录/result.json" "fact-review.json"
```

评分在复核运行目录新建 `evaluation.json` 与中文 `evaluation.md`，保留原始运行结果和交互。实际运行数量、告警与模型结果应以保存的证据为准。

## 两项指标分别记录

**分类主指标**为有效且正确的真缺陷/误报分类数，除以全部实际可复核告警数。弃权、协议错误、请求失败与过期结果保留在分母；另列二分类覆盖率、仅有效二分类上的条件正确率及混淆矩阵。未报告案例计入检测覆盖说明，不假装是模型正确识别；同一程序的多个告警也不是多个独立程序。

**解释事实指标**逐项检查方法/绑定、值及副作用、行号/位置、跨调用与路径关系，以及实际提供的证据和策略。标签分为正确、错误、无依据、无法裁定；正确率主分母包含全部抽取主张，另外显示仅已裁定事实的口径。没有声称行号时该项为 N/A，不能记成行号全部正确。

同时报告回复级全部事实获支持率和预定关键事实覆盖率，避免少说或漏掉关键路径反而显得更准确。单独列出“分类正确但解释含错误/无依据”的回复，未裁定及遗漏另列。逐条原文和证据保留供人工复验，未获人工签收前不把这些事实评分当成独立人类标注。

本轮不根据这些结果修改提示。后续若据此改进，须另立版本，并将本集合视为已经使用过的开发证据。

## 2026-11-03 实测

六个案例均完成真实构建、6 项 JUnit 与 Tai-e 分析，导出 64 条 SQL 观测；每例有 1 条项目告警，依赖告警为 0。六次冻结提示请求全部有效，无重试、弃权或宿主降级。

| 指标 | 结果 |
| --- | ---: |
| 分类正确率 / 二分类覆盖率 | 6/6，100% / 6/6，100% |
| 已核实原子事实正确率 | 112/116，96.6% |
| 整份解释全部事实获支持率 | 3/6，50% |
| 预定关键事实获支持 | 14/18，77.8% |

4 项事实错误集中在 G/I/K 的路径解释：G 把合并摘要限定为一个分支；I 把互斥的负 mode 与 mode=1 串成同次执行并扩大污染范围；K 忽略 mode=0 的后置覆盖。三者仍有真实可行污染路径，所以分类正确，但解释不能照单全收。引用的 22 项行号事实均正确，方法和值的事实核对也没有发现错误；J 没有引用 Java 行号，该项为 N/A。

分析流程耗时 191.27 秒，六次模型请求 22.92 秒，SDK 总用量 25,911 token（含缓存读取）。类型检查及新增 6 项宿主测试通过。事实划分和语义判定由辅助审阅给出，仍为 provisional/pending；没有已确认人工标注，也没有总体提效比较。原始六条告警均保留，冻结提示与实现未变。
